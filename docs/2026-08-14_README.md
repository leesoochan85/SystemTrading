## 1. 이번 개정의 핵심

이번 작업의 가장 큰 변화는 기존의 **소수 종목 순차 조회 방식**에서 벗어나 다음 구조로 전환한 것이다.

```text
KOSPI + KOSDAQ 기업주식 전체
        ↓
64bit Python + pykrx
        ↓
과거 일봉을 market_history.db에 저장
        ↓
장 시작 전 전략 계산값 사전 준비
        ↓
HighBreakout + PullbackTrend 후보 합집합 생성
        ↓
Kiwoom SetRealReg 1회 공통 등록
        ↓
주식체결 이벤트 발생 종목만 즉시 검사
        ↓
조건 충족 시 매수 / 매도
```

핵심 설계 원칙은 다음과 같다.

- 많은 종목을 Python Thread로 병렬 TR 조회하지 않는다.
- 과거 데이터 수집과 장중 실시간 감시를 분리한다.
- 전략별로 과거 일봉 DB를 중복 생성하지 않는다.
- 장중에는 pandas rolling 계산을 반복하지 않는다.
- 동일 종목을 여러 전략이 감시하더라도 실제 실시간 등록은 한 번만 수행한다.
- 실시간 전략도 StrategyManager의 계좌 안전장치를 통과해야 주문할 수 있다.

## 3. 전체 시스템 구조

### 기존 구조

```text
유니버스 생성
    ↓
종목 1 검사
    ↓
종목 2 검사
    ↓
...
    ↓
마지막 종목 검사
    ↓
다시 처음부터 검사
```

문제점:

- 종목 수가 늘어날수록 재검사 주기가 길어진다.
- 수백~수천 종목에서 Kiwoom TR 요청량이 증가한다.
- 전략마다 같은 데이터를 다시 계산할 가능성이 있다.
- 장 시작 직후 신호 대응이 느려질 수 있다.

### 현재 구조

```text
                    ┌──────────────────────┐
                    │ 64bit Python         │
                    │ pykrx                │
                    └──────────┬───────────┘
                               │
                               │ 과거 OHLCV
                               ▼
                    ┌──────────────────────┐
                    │ market_history.db    │
                    │ stock_master         │
                    │ daily_price          │
                    └──────────┬───────────┘
                               │
                               │ 장 시작 전 기준값 계산
                               ▼
        ┌────────────────────────────────────────────┐
        │            32bit Kiwoom                    │
        │ HighBreakoutStrategy                       │
        │ PullbackTrendStrategy                      │
        └───────────────────┬────────────────────────┘
                            │
                      공통 SetRealReg
                            │
                            ▼
                   Kiwoom 실시간 체결
                            │
                ┌───────────┴───────────┐
                ▼                       ▼
        HighBreakout 검사         PullbackTrend 검사
```

장중에는 **체결 이벤트가 들어온 종목만 즉시 검사**한다.

```text

```

기본 설정:

```text
과거 조회 범위: 약 180 달력일

최소 전략 사용 이력: 65 거래일
```

### 증분 수집

이미 충분한 데이터가 있는 종목:

```text
DB 마지막 저장 날짜 확인
        ↓

        ↓
누락 일봉 보충
```

DB가 최신이라면:

```text
외부 pykrx 요청 생략
```

즉 한 번 전체 DB가 구축된 이후에는 매일 모든 종목의 과거 180일을 다시 받지 않는다.

## 10. HighBreakoutStrategy

### 개념

KOSPI/KOSDAQ 기업주식 전체를 대상으로 직전 60거래일 신고가를 돌파하는 종목을 실시간 감시한다.

### 매수 조건

```text
현재가 > 직전 60거래일 최고가
AND
오늘 누적거래량 >= 직전 20거래일 평균거래량
```

추가 제한:

```text
MAX_POSITIONS = 10
```

### 장 시작 전 계산값

장중에 DataFrame rolling을 반복하지 않고 다음 값들을 미리 계산한다.

```text
breakout_price
volume_ma20
MA20 계산용 최근 종가 합계
```

### 장중 처리

```text
실시간 체결
→ 현재가
→ 누적거래량
→ 사전 계산값과 숫자 비교
```

### 현재 매도 조건

1. 매입가 대비 -5% 손절
   - 전량 시장가

2. 현재가가 동적으로 계산한 MA20 아래로 이탈
   - 전량 매도

### 최근 데이터 공백 종목 처리

전체 65거래일 이상 종목과 HighBreakout 계산 가능 종목 수가 다를 수 있다.

2026-08-14 기준:

```text
65거래일 이상 전체:     2,573종목
HighBreakout 계산 가능: 2,432종목
```

최근 거래 흐름이 충분하지 않은 종목은 신고가 전략에서 제외한다.

거래정지 후 오래된 데이터까지 강제로 이어붙여 직전 60거래일로 사용하는 방식은 현재 적용하지 않는다.

## 11. PullbackTrendStrategy

### 개념

상승 추세가 유지되는 가운데 현재가가 20일 이동평균선 부근까지 눌린 종목을 매수한다.

### 매수 조건

```text
MA5 > MA20 > MA60
AND
이격도 97% ~ 103%
AND
현재가 >= MA20
```

이격도:

```text
현재가 / MA20 × 100
```

`현재가 >= MA20` 조건이 있기 때문에 실제 진입 구간은 사실상 약:

```text
100% ~ 103%
```

이다.

### 장중 이동평균 계산

장중 현재가를 오늘의 임시 종가처럼 사용한다.

```text
MA5  = (직전 4일 종가 합 + 현재가) / 5
MA20 = (직전 19일 종가 합 + 현재가) / 20
MA60 = (직전 59일 종가 합 + 현재가) / 60
```

DataFrame 전체 rolling 대신 단순 합산으로 계산한다.

## 12. PullbackTrend 매도 조건

우선순위:

```text
1. -5% 손절
2. MA20 이탈
3. 거래량 급증 + 음봉
4. 전고점 다음 거래일 거래량 감소
5. 전고점 최초 도달 30% 부분매도
```

### 1. -5% 손절

```text
현재 수익률 <= -5%
```

→ 전량 시장가 매도

### 2. MA20 이탈

```text
현재가 < MA20
```

→ 전량 시장가 매도

### 3. 거래량 15% 증가 + 음봉

보유 중인 종목에서만 검사한다.

```text
오늘 누적거래량 >= 전일 거래량 × 1.15
AND
현재가 < 오늘 시가
```

→ 전량 시장가 매도

`prev_volume`은 프로그램 초기화 시 `market_history.db`에서 미리 읽어 메모리에 저장한다.

장중에는 단순 숫자 비교만 수행한다.

따라서 매 틱마다:

- DB 재조회하지 않음
- pykrx 조회하지 않음
- Kiwoom TR 조회하지 않음

### 4. 전고점 도달 시 30% 부분매도

매수 당시 직전 60거래일 최고가를 저장한다.

```text
previous_high = 매수 이전 직전 60거래일 최고가
```

가격이 전고점에 처음 도달하면:

```text
보유수량의 30%
```

를 시장가로 부분매도한다.

### 5. 전고점 다음 거래일 거래량 감소

```text
전고점 도달 다음 거래일
AND
15:20 이후
AND
오늘 누적거래량 < 전고점 도달일 거래량
```

→ 남은 수량 전량 시장가 매도

15:20 이후에 확인하는 이유는 오전에는 당일 누적거래량이 전일 전체 거래량보다 작은 것이 정상이라 잘못된 청산 신호를 줄 수 있기 때문이다.

## 14. 부분매도와 포지션 수량 관리

부분매도 실제 체결이 발생하면 `position_strategy`의 수량도 실제 체결량만큼 줄어든다.

예:

```text
10주 보유
↓
3주 부분매도 체결
↓
DB 수량 7주
```

전량 매도 후에는 실제 잔고에서 종목이 사라진 것을 확인한 뒤 포지션 정보를 삭제한다.

## 15. 주문 안전장치

event-driven 전략이 StrategyManager의 안전 상태를 우회하지 못하도록 `order_guard`를 사용한다.

신규 주문을 허용하려면 다음 조회가 정상적으로 완료되어야 한다.

- 미체결 주문
- 잔고
- 주문가능금액

Manager가 계좌 상태를 안전하지 않다고 판단하면:

```text
실시간 시세 수신       O
DB 데이터 갱신         O
전략 신호 계산         O
신규 주문              X
```

상태로 동작한다.

## 16. 자금 배분

자동매수 금액 계산에는 Kiwoom의:

```text
100%종목주문가능금액
```

을 사용한다.

미수 사용을 방지하기 위한 기준이다.

기존 StrategyManager:

```text
ORB 50%
일반 전략 50%
```

현재 `main.py`에서는 ORB를 실행하지 않으므로:

```text
ORB 배분 = 0%
일반 전략 = 100%
```

HighBreakout과 PullbackTrend가 일반 전략 공동 예산을 사용한다.

### 현재 남은 위험

두 event-driven 전략이 매우 짧은 시간 차이로 동시에 신호를 발생시키면 각 전략이 가지고 있는 로컬 예산 값 사이에 시간차가 생길 수 있다.

향후 개선:

```text
Manager 중심 중앙 예산 예약
```

구조를 추가하는 것이 좋다.

## 17. 장 종료 후 일봉 저장

32bit Kiwoom 프로그램은 장중 실시간 데이터로 당일 OHLCV를 만든다.

```text
시가
고가
저가
현재가 → 종가
누적거래량
```

장 종료 후 `market_history.db`의 `daily_price`에 저장한다.

따라서 프로그램이 장마감까지 정상 실행됐다면 다음날 외부 수집기가 같은 날짜를 처음부터 다시 받을 필요가 없다.

자동매매가 실행되지 못한 거래일이 있다면 다음 bootstrap 실행 시 pykrx가 누락 구간을 보충한다.

## 26. 현재 주의사항

### 1. 전략별 최대 보유 수

현재:

```text
HighBreakout = 최대 10종목
PullbackTrend = 최대 10종목
```

즉 계좌 전체 최대 10종목이 아니라 전략별 최대 10종목이다.

향후 StrategyManager에서 **계좌 전체 최대 보유 수**를 별도로 관리하는 것이 좋다.

### 2. 중앙 예산 예약 필요

두 전략이 거의 동시에 매수 신호를 만들면 로컬 예산 값 사이에 시간차가 생길 수 있다.

향후 Manager에서 주문 직전 예산을 예약하고 체결/실패 후 해제하는 구조를 검토한다.

### 3. 부분매도 상태

현재 부분매도 상태는 주문 요청 성공 기준으로 저장되는 부분이 있다.

향후 실제 Chejan 체결 확인 후:

```text
partial_exit_filled
```

같은 상태를 따로 기록하면 더 안전하다.

### 4. Pullback의 '종가'

매수 조건의 오늘 종가는 확정 종가가 아니라 장중 현재가를 사용한다.

따라서 현재 전략의 정확한 의미는:

> 장중 현재가격 기준 MA 정배열 + 20일선 눌림

이다.

### 5. pykrx

pykrx는 외부 웹 데이터 구조 변경 영향을 받을 수 있다.

bootstrap이 실패하면 빈 데이터 상태로 자동매매를 계속하지 말고 원인을 먼저 확인한다.

### 6. 32bit Kiwoom

2,000개가 넘는 종목의 실시간 이벤트를 32bit 프로세스에서 처리하므로 모의투자에서 CPU/메모리 사용량을 반드시 측정한다.

### 7. DB

`market_history.db`는 현재 전략 계산의 핵심 데이터다.

삭제 또는 초기화 전에 반드시 백업한다.
