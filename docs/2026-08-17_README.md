## 2. 웹 대시보드의 목적 재정의

기존에는 웹에 실제 계좌 잔고/예수금/실제 주문 결과를 중심으로 보여주는 방향도 포함되어 있었습니다.

오늘 기준 웹 대시보드의 주 목적을 다음으로 정리했습니다.

> **각 전략의 조건이 충족될 때 실제 계좌 제약과 관계없이 모두 가상 체결했다고 가정하고 전략 자체의 성과를 확인한다.**

따라서 가상매매는 실제 계좌의 다음 조건과 독립적입니다.

```text
예수금
주문 가능 금액
계좌 최대 보유종목 수
실제 주문 BLOCKED 여부
```

실제 주문은 그대로 안전 제한을 사용하지만 웹 전략 검증용 가상 포지션은 별도로 운용합니다.

## 3. 현재 전체 구조

```text
                    Kiwoom OpenAPI
                          │
                       실시간 틱
                          │
            ┌─────────────┴─────────────┐
            │                           │
            ▼                           ▼
       실제 전략                   가상 전략 엔진
            │                           │
            │                       메모리 캐시
            │                           │
         실제 주문                   최대 5초
            │                           │
            └──────────────┬────────────┘
                           ▼
                    monitoring.db
                           ▲
                           │ READ ONLY
                        FastAPI
                           ▲
                           │ HTTP
                      React/Vite
```

가장 중요한 원칙:

```text
React가 Kiwoom을 직접 접근하지 않는다.
FastAPI가 Kiwoom을 import/호출하지 않는다.
웹은 SQLite DB만 읽는다.
```

## 5. PullbackTrend 부분청산 처리

눌림목 전략은 전고점 도달 시:

```text
30% 부분청산
70% 잔여 보유
```

로 처리합니다.

예:

```text
진입 50,000
전고점 55,000

30% 청산 수익률 +10%
remaining_ratio = 0.70
```

30% 부분청산만 발생한 상태를 완전 종료 거래 1건으로 잘못 집계하지 않도록 가상 성과 계산 기준도 분리했습니다.

---

## 6. 기존 문제: 실시간 틱마다 SQLite write

처음 구조에서는 가상 포지션이 열린 뒤 실시간 틱이 올 때:

```text
DB에서 virtual_position 읽기
→ 현재가 계산
→ DB UPDATE
```

방식으로 동작할 수 있었습니다.

수천 종목을 실시간 등록하는 프로그램에서 가상 보유 종목이 늘어나면 불필요한 SQLite write가 증가합니다.

특히 웹은 초단위 모든 틱을 보여줄 필요가 없고 약 5초 정도의 최신값이면 충분합니다.

## 7. 변경 구조: 메모리 + 5초 스냅샷

`VirtualStrategyEngine`을 다음 방식으로 변경했습니다.

```text
실시간 틱
   │
   ├─ 전략 BUY/SELL 판단: 즉시
   │
   └─ 가상 현재가: 메모리만 갱신
                    │
                 dirty 표시
                    │
                 최대 5초
                    ▼
            monitoring.db 일괄 저장
```

핵심 필드:

```python
self.position_cache = {}
self.dirty_position_keys = set()
self.last_snapshot_at = 0.0
```

주기:

```python
SNAPSHOT_INTERVAL_SECONDS = 5.0
```

---

## 8. 중요한 이벤트는 즉시 DB 저장

5초 스냅샷은 현재가/미실현수익률과 같은 웹 표시용 상태에 적용합니다.

아래 이벤트는 지연시키지 않습니다.

```text
BUY
SELL
부분청산
완전청산
중요 runtime state
```

즉:

> **전략 판단을 5초마다 하는 것이 아니라, 전략 판단은 실시간이고 DB의 현재가 표시용 스냅샷만 최대 5초 간격이다.**

## 10. 가상 보유종목 실시간 감시 유지

가상 포지션이 열려 있는데 이후 전략의 신규 후보에서 제외되는 상황을 고려했습니다.

예:

```text
ValueQuality 가상 매수
→ 다음 재무 데이터 갱신에서 매수 후보 제외
```

이 경우에도 이미 열린 가상 포지션은 손절/익절 조건을 계속 검사해야 합니다.

따라서 `StrategyManager`의 실시간 등록 합집합에:

```text
실제 전략 후보
+
현재 열린 가상 포지션 코드
```

를 포함시켰습니다.

## 13. 5초 DB 스냅샷 테스트

테스트용 `T90001` 사용.

초기:

```text
진입가 100,000
현재가 103,000
수익률 +3.00%
```

메모리만 변경:

```text
103,000 → 104,000
메모리 수익률 +4.00%
```

즉시 flush:

```text
저장 건수 = 0

DB:
103,000
+3.00%
```

5.3초 후:

```text
저장 건수 = 1

DB:
104,000
+4.00%
```

최종 판정:

```text
5초 전 DB 미변경 : PASS
5초 후 현재가 반영: PASS
수익률 재계산     : PASS
updated_at 갱신   : PASS
```

따라서:

> **메모리 → 5초 스냅샷 → monitoring.db**

경로는 정상 동작하는 것을 확인했습니다.

## 14. React polling 테스트

프론트 화면 자동 갱신 검증을 위해 `T90001`의 DB 현재가를 7초 간격으로 변경했습니다.

```text
초기
103,000 / +3%

↓
105,000 / +5%

↓
102,000 / +2%

↓
107,000 / +7%

↓
104,000 / +4%
```

이 테스트의 목적:

```text
monitoring.db
     ↓
FastAPI
     ↓
React 약 5초 polling
     ↓
브라우저 자동 갱신
```

브라우저를 수동 새로고침하지 않고 값이 따라오는지 확인하는 방식입니다.
