# SystemTrading 작업 정리 - 2026-08-24

> 2026-08-24 작업의 핵심은 **장마감 일봉 저장 안전성 보강**, **React 전략 성과 시각화 개선**, **가상매매 반복 재진입 버그 감사/정리**, **같은 전략·종목의 당일 재진입 차단**입니다.

## 1. 오늘 작업 요약

오늘 진행한 작업은 크게 다음 다섯 가지입니다.

1. Kiwoom 장마감 일봉 저장용 OHLCV FID 보호

## 2. 장마감 일봉 저장 문제

장 종료 후 프로그램을 처음 실행했을 때 다음과 같은 상황을 확인했습니다.

```text
[StrategyManager] Kiwoom 당일 일봉 저장 결과: 0/2576종목
```

원인은 장중에 프로그램이 실행되지 않아 Kiwoom 실시간 OHLCV가 누적되지 않은 상태에서 장마감 일봉 저장을 시도했기 때문입니다.

정상 흐름:

```text
장중 실행
→ 현재가/시가/고가/저가/누적거래량 수신
→ 장마감 일봉 생성
→ market_history.db 저장
```

장 종료 후 첫 실행:

```text
장중 실시간 데이터 없음
→ 당일 일봉 생성 불가
→ 저장 SKIP
```

---

## 3. 장마감 일봉용 FID 강제 유지

실시간 FID 최적화 과정에서도 장마감 일봉 생성에 필요한 다음 필드는 반드시 유지하도록 수정했습니다.

```text
현재가
시가
고가
저가
누적거래량
```

주문 판단에 필요한 `(최우선)매수호가`도 유지합니다.

목적:

> 전략별 실시간 FID 최적화를 하더라도 장마감 OHLCV 생성에 필요한 필드는 절대 제거되지 않도록 한다.

## 4. 장 종료 후 첫 실행 SKIP 처리

`StrategyManager`에 오늘 장중 실행 여부를 기억하는 상태를 두고 장마감 저장을 분기하도록 변경했습니다.

```text
market_open_observed_date
```

동작:

```text
오늘 장중 실행 이력 있음
→ 장마감 일봉 저장 수행
→ 저장 0건이면 실제 문제로 판단

오늘 장중 실행 이력 없음
→ 장마감 일봉 저장 SKIP
→ 이후 64bit bootstrap으로 보완
```

따라서 예상 가능한 장외 첫 실행은 오류로 취급하지 않고, 실제 장중 실행했는데도 데이터가 없을 때만 오류를 유지합니다.



PullbackTrend의 30% 부분매도처럼 청산 비중이 다른 거래가 있으므로 단순 평균이 아니라 청산비중 가중평균을 사용합니다.

## 8. 가상 전략 성과지수 계산

현재 가상매매는 전략별 실제 현금계좌를 따로 운용하지 않습니다.

따라서 실제 원화 NAV가 아니라 각 가상 BUY를 동일한 투자금 1단위로 보는 equal-notional 방식으로 계산합니다.

청산된 부분:

```text
exit_ratio × exit_price / entry_price
```

미청산 부분:

```text
remaining_ratio × current_price / entry_price
```

전략 성과지수:

```text
(청산분 가치 + 미청산분 가치)
-------------------------------- × 100
(청산비중 + 미청산비중)
```

기준값은 `100`입니다.

---

## 9. MDD 계산

성과지수에서 최대낙폭을 계산합니다.

```text
drawdown_pct
=
strategy_index / 과거 최고 strategy_index - 1
```

예:

```text
100 → 110 → 115 → 105 → 90
```

최고점 `115`, 이후 저점 `90`이면:

```text
90 / 115 - 1
≈ -21.74%
```

추가 API:

```text
GET /api/strategies/{strategy_name}/virtual-index-history
```

React 화면:

```text
가상 전략 일별 성과지수
├─ 현재 누적 성과
├─ MDD
├─ 최고의 날
├─ 최악의 날
└─ 일별 수익률 선그래프
```

주의:

> 과거 장마감 미실현 상태는 기존 DB에 없기 때문에 MDD는 이 기능 적용 이후 쌓이는 스냅샷부터 의미가 있습니다.

## 11. 반복거래 감사 기준

`virtual_trade`에는 부분매도 leg도 개별 SELL로 저장되므로 단순 행 수만으로 중복을 판단하면 안 됩니다.

하나의 진입 round-trip 기준:

```text
strategy_name
+
code
+
entry_at
```

같은 전략+종목+날짜에 100% 완료 round-trip이 2개 이상 존재하면 첫 번째 이후를 당일 반복 재진입으로 판정했습니다.

## 14. 반복 재진입 원인

기존 `VirtualStrategyEngine` 흐름:

```text
BUY
↓
가상 포지션 생성
↓
SELL 조건 충족
↓
100% 청산
↓
virtual_position 삭제
↓
position_cache에서도 제거
↓
다음 실시간 틱
↓
BUY 조건이 계속 True
↓
새 BUY
↓
다시 SELL
```

즉 동시에 같은 전략+종목을 두 개 들고 있는 것은 막았지만, 전량청산 후 같은 날 다시 진입하는 것은 막지 못했습니다.

## 16. 당일 재진입 차단

DB만 정리하면 문제가 다시 생기므로 `VirtualStrategyEngine`에 재발 방지 로직을 추가했습니다.

정책:

```text
같은 전략 + 같은 종목
→ 하루 BUY 최대 1회

보유 중
→ 신규 BUY 없음

30% 부분매도 후 70% 보유
→ 기존 포지션 계속 관리
→ 신규 BUY 없음

당일 전량청산
→ 당일 재진입 금지

다음 거래일
→ 재진입 가능

같은 종목 + 다른 전략
→ 전략별로 각각 하루 1회 가능
```

## 20. 실제계좌 신규매수 거절 로그 중복

실제 계좌 최대 보유/대기 10종목 상태에서 동일 매수 조건이 계속 True이면 같은 거절 로그가 틱마다 반복될 수 있었습니다.

예:

```text
[StrategyManager] 신규매수 거절 -
계좌 최대 보유/대기 10종목 도달 /
다우기술(023590) /
PullbackTrendStrategy
```

이 문제는 주문 실패가 아니라 동일 상태의 콘솔 반복 출력 문제입니다.

해결 방향:

```text
전략 + 종목 + 거절사유
```

가 동일할 경우 일정 시간 동안 콘솔 출력만 제한합니다.

주문 거절 판단, 웹의 `last_buy_rejections`, 실제 exception/traceback은 그대로 유지합니다.
