# SystemTrading 작업 정리 - 2026-09-30

오늘 작업의 핵심은 신고가 매수를 직전 180거래일 최고가 기준으로 변경하고, 종목당 최대 투자 비중 10% 안에서 ATR 위험에 따라 매수 수량을 줄이며, 장 마감 전 MA 수익 청산과 웹 설정 기능을 추가한 것입니다.

기록 기준: 이 대화에서 작성한 코드와 개발 환경 검증 결과입니다. 사용자 PC의 다음 거래일 적용, 키움 주문 접수·체결, 실제 수익률 개선은 아직 확인되지 않았습니다.

## 1. 오늘 작업 요약

- 신고가 기준을 60거래일에서 180거래일로 변경
- 신고가의 95%부터 매수하던 조건을 제거하고 현재가가 신고가 이상일 때 진입
- 종목당 총자산의 10%를 최대 투자 비중으로 유지
- 신고가 전략에 거래당 총자산의 0.5% 계획 손실 기준 ATR 매수 수량 제한 추가
- ATR 청산과 함께 15:19~15:20 MA 수익 청산 추가
- MA 기간과 청산 비율을 웹 상세 화면에서 저장하는 기능 추가
- 설정 버전 충돌 방지 및 저장일 이후 첫 거래일 적용 구현
- 저장 버전과 매매 프로그램 적용 확인 버전을 화면에 분리 표시
- 단위 테스트 14개, API 응답 검사, Python 문법 검사, 프론트엔드 빌드 통과
- `npm run dev` 실행 폴더 오류 안내

## 2. HighBreakout 매수 조건 변경

### 변경 전

```text
현재가 >= 오늘을 제외한 직전 60거래일 최고가 × 0.95
```

### 변경 후

다음 조건을 모두 만족해야 매수 신호가 발생합니다.

```text
현재가 >= 오늘을 제외한 직전 180거래일 최고가
현재가 > 전일 완결 일봉 고가
당일 누적거래량 >= 최근 20거래일 평균거래량
최근 20거래일 평균거래대금 >= 20억원
유효한 Wilder ATR(14) 계산 가능
현재가 - 2 × ATR(14) > 0
```

180거래일은 일봉 개수 기준이며 달력상 180일이 아닙니다. 최고가보다 낮은 구간은 매수하지 않습니다. 구현상 최고가와 같은 가격도 조건에 포함됩니다.

예: 직전 180거래일 최고가 10,000원, 전일 고가 9,700원이라면:

| 현재가 | 가격 조건 판단 |
|---:|---|
| 9,500원 | 매수 불가 |
| 9,800원 | 매수 불가 |
| 10,000원 | 나머지 조건 충족 시 매수 가능 |
| 10,500원 | 나머지 조건 충족 시 매수 가능 |

매수 사유 코드는 `BREAKOUT_ENTRY`입니다. 실제 주문에는 계좌 안전조건, 사용가능 현금, 최대 보유/대기 10종목, 미체결 주문, 장 시간 및 기존 15:15 매수 마감 제한도 적용됩니다.

## 3. 종목당 최대 10% + ATR 위험 기반 매수 수량

### 계산 방법

신고가 전략의 실제 주문 수량은 두 수량 중 작은 값으로 결정합니다.

```text
계좌 위험 예산 = 총자산 × 0.005
1주당 초기 계획 손실 = 진입 ATR × 2
ATR 위험 수량 = floor(계좌 위험 예산 ÷ 1주당 초기 계획 손실)

매수 예산 = min(총자산 × 0.10, 사용가능 현금)
예산 수량 = floor(매수 예산 ÷ 수수료 반영 1주 비용)

최종 매수 수량 = min(예산 수량, ATR 위험 수량)
```

0.5%는 초기 ATR 청산선에 체결된다고 가정한 계획 손실입니다. 갭 하락, 슬리피지, 수수료, 주문 실패를 포함한 실제 최대 손실 보장이 아닙니다.

### 계산 예시

총자산 1,000만원, 주가 10,000원, 충분한 현금이라고 가정합니다. 아래 표는 수수료를 제외한 예시입니다.

| 진입 ATR | 초기 청산선 | ATR 위험 수량 | 10% 한도 수량 | 최종 수량 | 투자금 | 청산선 기준 계획 손실 |
|---:|---:|---:|---:|---:|---:|---:|
| 200원 | 9,600원 | 125주 | 100주 | 100주 | 100만원 | 4만원 |
| 500원 | 9,000원 | 50주 | 100주 | 50주 | 50만원 | 5만원 |

ATR이 크면 같은 주식 수량에서 초기 청산선까지의 손실이 커지므로 매수 수량을 줄입니다. 실제 코드에서는 매수 수수료를 반영하므로 표보다 수량이 적을 수 있습니다.

이 위험 수량 제한은 HighBreakout 실주문에 적용했습니다. 기존 가상매매는 실제 현금·수량과 독립적인 비중 모델이므로, 웹 가상 수익률만으로 이 자금관리 방식의 계좌 성과를 비교할 수 없습니다.

## 4. 기존 ATR 청산 유지

```text
ATR 기간 = Wilder ATR(14)
초기 청산선 = 실제 평균 매입가 - 2 × 진입 직전 ATR
추적 청산 후보 = 진입 이후 최고 완결 종가 - 3 × 완결 일봉 ATR
최종 청산선 = max(기존 청산선, 초기 청산선, 추적 청산 후보)
```

- 당일 미완성 봉을 제외하고 완결 일봉으로 갱신합니다.
- 갱신한 일봉 청산선은 다음 거래일부터 사용합니다.
- 청산선은 하락하지 않습니다.
- 현재가가 청산선 이하이면 잔량 시장가 매도 신호가 발생합니다.
- ATR 기간·배수의 웹 편집 기능은 이번 작업에 포함하지 않았습니다.

## 5. 장 마감 전 MA 수익 청산

기본값은 `MA5 × 0.97`입니다. ATR 조건을 먼저 검사하고 ATR 매도 신호가 없으면 다음 조건을 검사합니다.

```text
검사 시간: 15:19:00 이상 ~ 15:20:00 미만
수익 조건: 현재가 > 평균 매입가
매도 조건: 현재가 <= 고정한 MA 기준선
```

MA 기간이 N, 설정 비율이 R이면:

```text
예상 MA(N) = (직전 N-1거래일 완결 종가 합계 + 해당 종목의 15:19 이후 첫 틱 가격) ÷ N
고정 청산선 = 예상 MA(N) × R
```

15:19 이후 첫 틱의 기준 가격을 상태에 저장하고 그날 검사 구간 동안 유지합니다. 최종 종가로 계산한 확정 MA가 아니라 장중 가격을 포함한 예상 MA입니다.

### 예시: MA10 × 0.95

```text
직전 9거래일 종가: 모두 12,000원
15:19 이후 첫 틱: 12,000원
예상 MA10: 12,000원
청산선: 12,000 × 0.95 = 11,400원
평균 매입가: 10,000원
이후 현재가: 11,300원
```

현재가가 매입가보다 높고 청산선 이하이므로 시장가 매도 신호가 발생합니다. 해당 구간에서 기준선에 도달하지 않으면 MA 조건으로 매도하지 않습니다.

### 주문 방식의 구분

이번 구현은 증권사에 미리 조건부 스탑 주문을 등록하는 방식이 아닙니다. 프로그램이 실시간 틱으로 가격을 감시하다가 조건 충족 시 시장가 주문을 요청합니다.

- 해당 시간에 틱이 없으면 MA 검사가 진행되지 않을 수 있습니다.
- 프로그램 또는 실시간 연결이 중단되면 이 조건 감시도 중단됩니다.
- 15:20부터 MA 검사는 종료되며 ATR 관리는 기존 흐름을 따릅니다.
- 주문 요청 후 실제 접수·체결 여부는 별도로 확인해야 합니다.
- 수익 조건은 가격 비교이며 수수료·세금을 뺀 순이익 보장이 아닙니다.

매도 사유 코드: `ATR_INITIAL_STOP`, `ATR_TRAILING_STOP`, `MA_PROFIT_EXIT`.
기존 기록의 `MA5_PROFIT_EXIT`도 조회 호환을 유지합니다.

## 6. 웹에서 MA 설정 변경

신고가 돌파 상세 화면에 설정 패널을 추가했습니다.

| 항목 | 허용 범위 | 기본값 |
|---|---|---|
| 이동평균 기간 | 2~60거래일 정수 | 5 |
| 청산 기준 비율 | 0.80 이상 1.00 미만 | 0.97 |

예: 기간 `10`, 비율 `0.95`를 입력하고 **다음 거래일 설정 저장**을 누릅니다.

API:

```text
GET /api/strategies/HighBreakoutStrategy/ma-settings
PUT /api/strategies/HighBreakoutStrategy/ma-settings
```

저장 요청 예:

```json
{
  "ma_period": 10,
  "exit_ratio": 0.95,
  "expected_revision": 0
}
```

`expected_revision`은 화면에서 읽은 최신 버전입니다. 다른 화면에서 먼저 변경했다면 HTTP 409로 충돌을 알리고 덮어쓰지 않습니다. 범위를 벗어난 입력은 HTTP 422로 거절합니다.

## 7. 다음 거래일 적용과 확인

설정은 `strategy_settings.db`에 저장합니다.

| 테이블 | 용도 |
|---|---|
| `ma_settings` | 설정 버전, MA 기간, 비율, 저장 날짜·시간 |
| `ma_settings_applied` | 매매 프로그램 적용 확인 버전·날짜·시간 |

매매 프로그램은 저장 날짜가 오늘보다 이전인 설정 중 최신 버전을 선택합니다.

```sql
WHERE saved_date < 오늘날짜
ORDER BY revision DESC
LIMIT 1
```

적용은 장중 전략 초기화 또는 해당 날짜의 첫 유효 실시간 틱 처리 시 이루어집니다. MA 청산 평가 경로에서도 설정 확인 함수를 호출합니다. 정확히 09:00에 예약 실행하는 방식은 아닙니다.

- 장중 저장한 설정은 당일 반영하지 않습니다.
- 당일 프로그램을 재시작해도 당일 저장 버전은 제외합니다.
- 같은 날 여러 번 저장했다면 다음 거래일에 그중 최신 버전을 선택합니다.
- 매매 프로그램을 실행하지 않으면 웹만 켜도 적용 확인은 갱신되지 않습니다.
- 웹과 매매 프로그램은 같은 DB 경로를 사용해야 합니다.
- 날짜·시간은 실행 PC의 로컬 시간을 사용하므로 한국 시장 운영 PC의 시간대를 확인합니다.

로그 예:

```text
[HighBreakout] MA 청산 설정 적용: v1 / MA10 × 0.950 / 20261001
```

웹은 약 5초마다 읽어 `저장한 설정`과 `매매 프로그램 적용 확인`을 표시합니다. 두 버전과 설정값이 일치하면 적용 확인을 할 수 있습니다. 표시된 적용 기록은 프로그램 생존 확인이나 주문 체결 확인이 아닙니다.

## 9. 실행 폴더 오류 해결

프로젝트 최상위에서 `npm run dev`를 실행하면 그 위치에 `package.json`이 없어 ENOENT가 발생합니다.

프로젝트 최상위에서:

```cmd
cd web_frontend
npm run dev
```

의존성이 없다면 `web_frontend` 안에서 먼저 `npm install`을 실행합니다. FastAPI는 별도 CMD에서 프로젝트 최상위의 `python run_web_api.py`로 실행합니다.
