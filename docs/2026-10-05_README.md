# 2026-10-05 모멘텀 수축 돌파 가상 비교

후속 변경: 첫 구간 데이터 검사·선택적 틱 기록·C 재현 도구는 [2026-10-08 구현 안내](2026-10-08_breakout_implementation.md)를 확인한다. 아래 검증 개수와 첫 구간 설명은 10월 5일 최초 구현 기준이다.

PDF와 동영상 화면의 조건을 `MomentumContractionStrategy`로 추가했다.
새 전략은 가상 전용이다. `StrategyManager`도 A/B/C 이름의 실제 매수 요청을 차단한다.
`main.py`의 기존 세 전략은 기존 실계좌 주문 흐름을 계속 사용하므로, 새 전략을 추가했다고 전체 프로그램이 가상 전용으로 바뀌지는 않는다.

## 자료의 조건과 구현 선택

참고 자료는 Qullamaggie의 `3 TIMELESS setups that have made me TENS OF MILLIONS!` PDF, 특히 3–4페이지와 이전에 확인한 동영상 화면이다.
PDF는 2021년 자료이고 동영상은 음성·자막 없이 화면에서 확인한 값만 사용했다.
ADR 수식은 저자의 [공식 FAQ](https://qullamaggie.com/faq/)에서 확인했다.
[원문 설명](https://qullamaggie.com/3-timeless-setups-that-have-made-me-tens-of-millions/)도 함께 참고한다.

설정은 `config/momentum_contraction.json`에 있다. 횡보·저점 상승은 눈으로 판단하는 패턴을 수치로 근사한 것이므로 원저자의 재량 판단과 같지는 않다.

| 항목 | 자료에서 확인한 내용 | 구현 기본값 / 해석 |
| --- | --- | --- |
| 모멘텀 | PDF의 1·3·6개월 상승 상위 1–2%; 영상의 `C / MINL126` | 기본 `video_low126`: 종가 / 최근 126봉 최저 저가 상위 2%. `pdf_returns`는 21·63·126봉 실제 종가 수익률 각각 상위 2%의 합집합 |
| ADR | 영상의 `ADR % 20 days > 3.5` | `100 × (20봉 high/low의 평균 − 1) > 3.5` |
| 선행 상승 | PDF의 대략 30–100% 상승 후 정리 | 횡보 직전 60봉의 마지막 종가 / 같은 구간 최저 종가 상승률 ≥ 30%. 측정 방식과 60봉은 실험값; 100% 상한은 두지 않음 |
| 횡보 | PDF의 약 2주–2개월, 높아지는 저점과 좁아지는 범위 | 최근 20봉. 마지막 5봉 평균 TR / 앞선 15봉 평균 TR ≤ 0.7, 마지막 5봉 최저 저가 ≥ 직전 5봉 최저 저가. 실험값이며 동일 저점도 허용 |
| 유동성 | 현재 저장소의 거래대금 조건 | 최근 20봉 `close × volume` 평균 ≥ 20억원. 한국시장 적용값 |
| 진입 | PDF의 opening range 또는 일봉 돌파 | 첫 5분 관측 최고가와 20봉 횡보 최고가 중 큰 값 초과. 5분은 실험 선택 |
| 초기 손절 | 진입 당일 저가, ATR/ADR보다 넓지 않게 | 진입 시점의 FID 당일 저가 고정. 모델 체결가 − 저가 ≤ 전일 완결 ATR(14) × 1 |
| 부분 매도 | 3–5일 뒤 1/3–1/2 청산 | D+4 거래일 이후 최초 순이익 틱에 초기 수량 약 1/3 매도. 수익 중에만 실행하는 조건은 구현 선택 |
| 잔량 | MA10/20의 확정 종가 이탈 | 부분 체결 뒤 전일 확정 종가 < 전일 MA10이면 다음 관측 틱에 전량 청산 |

순위는 ADR·유동성·패턴 조건을 적용하기 전, 최신 일봉과 충분한 이력이 있는 활성 기업주식 전체에서 계산한다.
상위 개수는 `ceil(유효 종목 수 × 비율)`로 정하고 동률은 종목코드 순서로 결정한다. 작은 유니버스에서는 실제 비율이 2%보다 커질 수 있다.
`pdf_returns`의 세 기간 합집합은 한 기간만 사용하는 것보다 후보가 많을 수 있다.
일봉은 모두 판단일 이전 행만 읽고, 마지막 봉이 직전 예상 거래일보다 오래된 종목은 순위 대상에서 제외한다.
`C / MINL126`은 6개월 실제 수익률과 다른 지표이므로 두 모드를 구분한다.

## A/B/C 비교

세 계좌는 같은 실시간 틱을 받아 각각 독립적으로 현금과 보유 종목을 관리한다.
기존 웹의 비중 기반 가상매매와 별도로 기록하며, 기존 가상 수익률 지수와 바로 비교하지 않는다.

| 계좌 | 매수 | 매도 |
| --- | --- | --- |
| A `HighBreakoutBaselinePaper` | 기존 180봉 신고가·전일 고가·누적 거래량 조건 | 기존 초기 2ATR / 추적 3ATR + 15:19 MA 수익 청산 |
| B `HighBreakoutFilteredPaper` | A 조건 + 새 전략의 일봉 후보 필터 | A와 동일 |
| C `MomentumContractionStrategy` | 새 후보 + 첫 5분/횡보 고가 돌파 | 고정 당일 저가 손절, 부분 매도, 확정 종가 MA10 이탈 |

공통 기본값은 초기 현금 1,000만원, 종목당 최대 총자산 10%, 최대 10종목, 손절 예상 손실 예산 총자산 0.5%다.
수량은 정수이며 매수 수수료까지 포함해 현금·종목 비중·손절 위험 한도 중 가장 작은 수량을 사용한다.
손절 예상 손실에는 설정한 매도 수수료·세금·슬리피지도 반영한다.
가격 급변이나 갭에서는 관측 틱에 청산하므로 실제 모형 손실이 0.5%를 넘을 수 있다.

가상 체결 비용 기본값:

| 비용 | 기본 가정 |
| --- | --- |
| 매수 수수료 | 0.035% |
| 매도 수수료 | 0.035% |
| 매도 세금 | 0.200% |
| 슬리피지 | 매수·매도 각각 5bp |

이 숫자는 실험용 가정이며 현재 증권사 수수료나 현행 세율을 뜻하지 않는다. 평가 전에 사용 계좌 조건에 맞춘다.
체결가는 관측 틱에 슬리피지를 더한 뒤 매수 올림, 매도 내림으로 계산한다. 실제 거래소 호가 단위·호가 잔량·미체결은 재현하지 않는다.
평가액은 현금 + 잔량 × 관측 현재가이며 보유분의 향후 매도 비용은 매도 시점에 차감한다.

## 상태와 재시작

매수·매도·부분 체결은 현금, 수량, 비용, 거래 기록, 중요 상태를 같은 SQLite 트랜잭션으로 저장한다.
같은 계좌가 같은 종목을 당일 매수한 이력이 있으면 전량 청산 후에도 재진입하지 않는다.
부분 청산 수량은 `floor(초기 수량 × 비율)`이며 최소 1주다. 초기 1주 포지션은 부분 매도를 건너뛰고 D+4부터 확정 종가 MA 청산을 허용한다.
부분 체결 후 잔량의 손절선은 비용·설정 슬리피지를 포함한 손익분기선 이상으로 올리고 다시 낮추지 않는다.
진입 당시 저가는 초기 값으로 보존하며 나중에 형성된 당일 저가로 초기 손절을 다시 계산하지 않는다.
고정 손절을 먼저 검사하므로 후보/MA 데이터 조회 실패 중에도 저장된 손절선으로 청산한다.
보유 종목은 후보에서 빠져도 공통 실시간 등록에 계속 포함한다.

현재가는 메모리에서 갱신하고 약 5초마다 DB에 저장한다. `paper_equity`는 계좌별 날짜별 마지막 관측값을 보관한다.
누적 수익률은 비용 차감 평가액 기준이고 관측 최대 낙폭은 5초 스냅샷에서 나온 최고 평가액 대비 최저 낙폭을 누적 보존한다.
장중 회복이나 재시작으로 최대 낙폭이 사라지지 않는다. 5초 사이의 더 큰 낙폭은 이 지표에 포함되지 않을 수 있다.
완료 거래의 승률·평균 수익률·이익합/손실합은 부분 청산만으로 집계하지 않고 잔량까지 모두 팔린 진입 건에서 계산한다.

## 실행과 실험 변경

1. 기존 설치 가이드에 따라 `market_history.db`와 활성 종목 마스터를 준비한다. 새 계산에는 최소 127개 완결봉이 필요하고 A/B의 신고가에는 기존 180봉이 필요하다.
2. 최초 실행 전에 `config/momentum_contraction.json`의 전략 값과 비용 가정을 확인한다.
3. 기존대로 `main.py`, `run_web_api.py`, React를 실행한다. C 진입을 관측하려면 매매 프로그램의 로그인·지표 계산·실시간 등록까지 개장 전에 끝내야 한다.
4. 전체 전략 화면에서 **모멘텀 수축 돌파**를 연다. 후보 단계별 개수, 진입 대기 사유, A/B/C 평가액·관측 MDD, C 보유/부분 청산/거래 기록을 확인한다.

장중 늦게 실행하면 C는 당일 첫 구간을 추측하지 않고 신규 진입을 보류한다. 첫 5분에 해당 종목의 틱을 하나도 받지 못한 경우도 보류한다.
등록이 개장 전 완료되더라도 일부 틱 유실은 실제 opening range와 차이를 만들 수 있다.
체결시간 FID가 없거나 역순/30초 초과 지연/5초 초과 미래 틱이면 A/B/C 가상 체결을 진행하지 않는다.
신규 진입 마감은 저장소의 기존 15:15 정책을 따른다.

가상 기록은 기본적으로 `monitoring.db`의 아래 별도 테이블에 저장한다:

```text
paper_account / paper_position / paper_trade
paper_equity / paper_watchlist / paper_run_status
```

동일 실험 DB의 설정은 첫 실행 값으로 고정된다. 중간에 JSON을 바꾸면 시작 시 오류가 발생한다.
기존 기록을 유지하며 다른 값을 시험하려면 별도 DB 경로를 지정한다. 매매 프로그램과 API를 실행할 CMD **각각** 같은 절대 경로를 설정한다:

```cmd
set SYSTEMTRADING_PAPER_DB=C:\경로\SystemTrading\paper_experiment2.db
```

그 뒤 새 설정으로 매매 프로그램과 API를 다시 실행한다. 이전 DB는 남겨 둔다.
API는 지정한 파일을 조회만 하며 파일이 없으면 `ready: false`를 반환한다.
조회 API는 `GET /api/strategies/MomentumContractionStrategy/paper-comparison`이며 실전 활성화 API는 없다.

## 기존 신고가 전략 연결 수정

- 실매수 요청에 `entry_atr`와 `initial_atr_multiple`을 넘겨 Manager의 기존 ATR 수량 계산이 필요한 값을 받도록 했다.
- 누락되어 있던 `evaluate_sell_signal`을 연결해 기존 가상계좌와 A/B도 동일한 ATR·MA 매도 판정을 사용한다.
- 웹에 저장된 MA 설정을 저장일 이후 거래일에 읽고 적용 확인을 기록한다.
- ATR 청산이 우선이며, MA 수익 청산은 `15:19:00 <= 시간 < 15:20:00`에만 검사한다. 기본 MA5 × 0.97이다.
- 첫 검사 틱을 고정해 `(직전 N−1개 완결 종가 합 + 기준 틱) / N × 비율`을 계산한다. 현재가가 매입가보다 높고 이 선 이하일 때 청산한다. C의 확정 종가 MA10 규칙과는 다르다.

이 연결 수정은 기존 신고가 전략의 **실계좌 매도 및 매수 수량 결정에도 적용**된다. Windows/Kiwoom에서 운영하기 전에 수정 내용을 확인한다.

## 검증과 남은 범위

```cmd
python -m unittest discover -s tests -v
python -m compileall -q api strategy util web_api tests
cd web_frontend
npm run build
```

자동 테스트는 실제 주문 없이 합성 일봉과 틱을 사용한다. 웹 API 테스트를 포함하므로 `requirements-web.txt`와 `httpx`, 기존 실행 의존성인 `pandas`·`requests`가 필요하다. Qt/Kiwoom은 테스트에서 대체한다.
39개 테스트가 통과했다. ADR·순위·당일봉 제외·지연 틱 차단, 실제 전략의 동일 틱 처리, 비용/현금/정수 수량, 손절 갭, 부분 청산/재시작, 중복 writer, 당일 재진입, 최대 낙폭 복구, 실주문 차단, 기존 ATR·MA 설정 연결, 읽기 API와 범위 제한을 검증했다.
이는 전략 수익성을 검증한 결과가 아니다. 현재 저장소에 분봉/과거 틱이 없어 opening range를 사용하는 과거 백테스트는 구현하지 않았다.
Linux 검증 환경에서 Windows 32bit Kiwoom ActiveX 로그인·실시간 연결·주문 실행을 확인하지 못했다.
보유 거래일 수는 시장 DB에 저장된 완결 날짜 수로 계산하므로 누락된 날짜가 있으면 부분 청산 시점이 늦어질 수 있다.
직전 거래일과 세션 시간은 기존 `util/time_helper.py`를 사용한다. 휴장일·특별 개장 시간 목록은 운용 연도에 맞게 관리해야 한다.
