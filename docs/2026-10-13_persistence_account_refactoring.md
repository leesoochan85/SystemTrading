# DB·주문·잔고 관리 모듈 분리 — 2026-10-13

첫 번째 미사용 코드 정리 패치 적용 상태에서 진행한 후속 리팩토링이다. 첫 번째 패치의 기준 GitHub main은 `24f50dc59c7997c3df5bcea04b0c0463d3aec80c`이며, 이번 작업은 그 원본에 첫 패치를 적용한 코드를 기준으로 한다. 원격 저장소 쓰기 권한 제한이 앞서 확인되어 GitHub 반영 대신 로컬 적용 패치를 제공한다.

## 구현한 구조

| 파일 | 책임 |
|---|---|
| `util/db_helper.py` | 기존 API 호환 창구. 기존 28개 함수의 이름·인자와 `MONITORING_DB`, `POSITION_DB` 설정 유지 |
| `util/db_context.py` | 호출 단위 DB 경로·시각 설정, 연결·커밋·롤백·닫기 관리 |
| `util/db_schema.py` | 테이블·인덱스 생성과 기존 스키마 마이그레이션 |
| `util/position_repository.py` | 전략 보유정보·실제 매수 체결 수량·평균매입가·매도 잔량 관리 |
| `util/order_repository.py` | 전략 신호·주문 이벤트·체결 기록·비용·당일 손익 조회 |
| `util/performance_repository.py` | 보유 스냅샷·일별 자산·전략 성과 저장 |
| `strategy/order_coordinator.py` | 신규매수 승인, 공용현금 예약, 계좌 슬롯 제한, 오래된 매수 미체결 취소와 정리 |
| `strategy/account_state.py` | 자금·잔고 조회 안전 상태, 실제 잔고와 DB 수량 동기화, 전략 종료 알림·보유 삭제 확인 |

기존 사용처는 계속 `from util.db_helper import save_trade_fill`처럼 호출한다. DB 함수 안에서는 같은 `RepositoryContext`를 하위 호출에 전달한다. 이미 import한 함수도 호출 시점의 `db_helper.MONITORING_DB`·`POSITION_DB`를 사용하며, 테스트의 임시 DB 경로 설정도 유지된다. 새 저장 모듈은 명시적 context로 직접 테스트할 수 있다.

주문·잔고 객체는 상태를 복사하지 않는다. 예약 현금, 처리 중인 종목 집합, 조회 실패 플래그, 취소 대기, 삭제 확인 횟수는 기존 Manager 객체에 그대로 존재한다. Manager의 공개 메서드는 새 객체로 위임하므로 기존 전략 콜백과 호출 경로를 유지한다. 객체는 호출 시 가볍게 생성되는 실행 어댑터이며 새 타이머·스레드·잠금을 추가하지 않는다.

## 그대로 유지한 정책

- 증권사 신규 주문 직전 공용현금을 선예약한다.
- 보유·매수대기·예약 종목의 합집합을 계좌 한도로 판단한다.
- 최대 10종목, 종목당 총자산 최대 10%와 모멘텀 위험 수량 제한을 유지한다.
- 모멘텀 신규매수 opt-in과 기존 보유 매도관리를 유지한다.
- 주문·잔고 조회 실패 시 신규 주문을 막고 기존 상태를 보존한다.
- 수동 부분매도는 실제 잔고로 수량을 맞추고 전량매도 삭제는 기존 2회 확인 규칙을 유지한다.
- 매수 예약 복구는 현재 실행 중인 전략으로 소유가 확인된 행만 대상으로 한다. DB에 없는 수동 보유를 자동으로 전략에 귀속하지 않는다.
- 체결번호 중복 방지, 분할 매도 합산, 수수료·세금 누적값 교체 방식과 손익 계산을 유지한다.
- 매매·웹 API·A/B/C 비교계좌의 DB 파일명과 테이블을 유지한다.

SQLite 연결은 트랜잭션 컨텍스트를 종료한 뒤 실제 연결을 닫는다. 기존과 같은 조건으로 정상 종료는 커밋하고 예외는 롤백한다. 여러 DB 간 작업을 하나의 원자적 트랜잭션으로 바꾸는 변경은 없으며, 체결 기록 후 포지션 반영이라는 기존 기록 순서를 유지한다.

## 테스트 환경 안내

앞서 Python 3.9 32bit 테스트 로그에서 3개 웹 API 테스트가 `fastapi` 미설치로 실패했다. 매매 실행 환경과 전체 테스트 환경을 구분해 재현할 수 있도록 `requirements-test.txt`와 `run_tests.bat`을 추가했다.

프로젝트 루트 CMD에서:

```cmd
webenv\Scripts\python.exe -m pip install -r requirements-test.txt
run_tests.bat
```

`run_tests.bat`은 webenv와 테스트 의존성을 먼저 확인하고 전체 unittest를 실행한다. 패키지를 자동 설치하거나 테스트를 생략하지 않는다. 실패 시 오류 코드가 유지된다. 실제 매매는 계속 `start_trading.bat`의 `py -3.9-32 main.py`로 실행한다.

프론트엔드 코드와 웹 API 엔드포인트는 이번 단계에서 변경하지 않았다. 사용자 요청으로 앞서 제시한 React 동시 실행용 `start_web_api.bat` 수정도 이번 패치의 수정 대상에 포함하지 않아 로컬 BAT 수정과 충돌하지 않도록 했다.

## 적용 방법

제공 ZIP의 두 패치 중 현재 상태에 맞는 하나만 사용한다.

| 현재 로컬 상태 | 사용할 패치 |
|---|---|
| 첫 번째 미사용 정리 패치를 적용한 상태 | `refactor_phase2_after_cleanup.patch` |
| 첫 번째 패치 적용 전, 기준 main `24f50dc` 상태 | `refactor_all_from_24f50dc.patch` |

매매·웹 프로세스를 종료한 뒤 선택한 패치를 프로젝트 루트에 복사한다. 첫 번째 패치 적용 상태에서는:

```cmd
git status
git apply --check refactor_phase2_after_cleanup.patch
git apply refactor_phase2_after_cleanup.patch
webenv\Scripts\python.exe -m pip install -r requirements-test.txt
run_tests.bat
git diff --stat
```

`--check`가 실패하면 수정 충돌이나 기준 코드 차이를 먼저 확인한다. 두 패치를 연속으로 적용하지 않는다. 이전 제공 패치에 이어 적용하는 것이 기본 경로이며, 이번 패치는 운영 DB를 삭제하지 않는다.
