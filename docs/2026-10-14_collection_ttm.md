# 2026-10-14 수집 시간 개선과 분기별 TTM 우량주 지표

기준 소스: GitHub main `1f5eeab9408cc3398816ef62baa03fad25b12d76`.
사용자가 선택한 최근 4분기 합산(TTM) 방식으로 구현한다.

## 동작 변경

| 항목 | 기존 | 변경 |
|---|---|---|
| 매출총이익률·총자산회전율 | 최근 연간 실적 | 최신 분기까지의 최근 4분기 합산 |
| 정상 재무 응답 | 24시간 캐시 | 최대 7일 캐시 + 새 정기공시·정정공시 접수번호 감지 시 회사별 갱신 |
| 데이터 없음 | 캐시 없음 | 6시간 캐시, 공시 목록 응답은 최대 15분 |
| 같은 기준일 재실행 | 처음부터 재검사 | 시가총액·상장주식 수·기업 식별·공시 토큰·계산 버전이 같으면 완료 상태 재사용(6시간) |
| 새 거래일 | 전체 보고서 재조회 가능 | 시장 시가총액은 조회하고 재무 캐시로 전체 종목 지표 재계산 |
| 연결 오류 | 한 번 실패하면 종료 | 처음 포함 최대 3회, 재시도 대기 1초·2초 |
| 이력 부족 종목 | 매번 400일 조회 | 최근 전체 범위 저장 후 7일간 증분 갱신, 주기적으로 전체 조회 |
| 재무만 실행 | Python 경로 직접 지정 | `update_market_data.bat value` 지원 |

최초 구축과 강제 수집은 여전히 시간이 걸린다. 대기시간(일봉 1초 / DART 요청 0.3초)은 유지하며 요청 수를 줄인다. 일봉의 날짜별 전체 시장 일괄 조회와 병렬 요청은 이번 패치에 포함하지 않았다.

## 분기별 계산

반기·3분기 손익계산서의 `thstrm_amount`는 3개월 금액이므로 `thstrm_add_amount` 누적금액을 사용한다. 1분기만 누적금액이 누락됐을 때 당기금액으로 대체한다.

```text
TTM 매출 = 전년도 연간 매출 + 당해연도 누적 매출 - 전년도 동일 기간 누적 매출
TTM 매출총이익 = 전년도 연간 매출총이익 + 당해연도 누적 매출총이익 - 전년도 동일 기간 누적 매출총이익
TTM 매출총이익률 = TTM 매출총이익 / TTM 매출 × 100
TTM 총자산회전율 = TTM 매출 / ((전년도 동일 분기말 자산 + 최신 분기말 자산) / 2)
```

예: 연간 매출 1,200, 금년 반기 누적 매출 900, 전년 반기 누적 매출 600이면 TTM 매출은 1,500이다. 연간 매출총이익 480, 금년 반기 450, 전년 반기 240이면 TTM 매출총이익은 690이므로 매출총이익률은 46%다. 전년 반기말 자산 600·금년 반기말 자산 1,400이면 평균자산은 1,000, 회전율은 1.5회다. 예시는 합성 데이터다.

최신 사업보고서만 사용하는 경우 해당 연간 실적 자체가 4분기 합산이며, 자산은 연초·연말 평균이다. 연결/별도 기준을 혼합하지 않는다. 매출총이익 계정이 없으면 각 기간의 매출-매출원가로 계산한다. 누락·모호한 값은 임의로 0으로 채우지 않는다.

매수 필터 숫자는 유지: PER 0 초과~15, PBR 0 초과~1, TTM 매출총이익률 30~95%, TTM 회전율 1~10회. 지표 기준이 바뀌었으므로 기존 후보 8개와 새 후보 수는 달라질 수 있다. 이전 연간 스냅샷은 출처 메타데이터로 구분하며 재계산 전 후보에 사용하지 않는다. 보유 상태와 거래 이력은 삭제하지 않는다.

## 캐시와 재개 정책

- KRX 시가총액·상장주식 수는 매 수집 시작 시 조회한다. 후보 8개로 조회 범위를 좁히지 않는다.
- 정기공시 목록은 회사별 요청 대신 전체 시장을 페이지별 조회한다. `last_reprt_at=N`으로 정정을 포함한다. 첫 확인은 최근 7일, 이후에는 마지막 확인일보다 하루 전부터 현재 기준일까지 조회한다.
- 새 접수번호는 해당 회사의 응답 캐시와 완료 상태를 변경한다. 회사당 가장 최근 접수번호 토큰으로 연간·분기·주식 수 응답을 함께 갱신한다. 정기공시 확인 간격이 60일을 넘으면 전체 응답 재검증용 토큰을 바꾼다. 정상 응답의 7일 TTL도 주기적 재검증 수단이다.
- 모든 공시 페이지를 읽기 전에 실패하면 확인 지점을 전진시키지 않는다. 인증/한도 오류에서 기존 캐시를 근거 없이 최신으로 처리하지 않는다.
- 같은 시가총액 기준일의 완료 상태는 최대 6시간 유효하다. 정상 저장과 데이터 검증 제외는 완료 기록을 남기고, 통신·인증·한도 오류는 남기지 않는다.
- `--force`는 보고서 응답 캐시와 완료 상태를 무시한다. API 요청량이 늘어날 수 있다.
- 기존 버전의 중단 위치에는 체크포인트가 없으므로 패치 후 첫 실행은 목록 처음부터 새 TTM 지표를 만든다. 정상적인 기존 응답 캐시는 재사용 가능하다.
- 신규 보고서의 API 반영 지연, 15분 목록 캐시, 6시간 데이터 없음 캐시 때문에 즉시 반영을 보장하지 않는다. 시가총액 기준일은 원래처럼 전 거래일이며 미래 접수 보고서는 거부한다.
- 동일 프로젝트에서 수집기를 여러 개 동시에 실행하지 않는다. 한 프로세스에서 순차 수집하는 운영 방식이다.

## 실행

매매 프로그램을 종료하고 프로젝트 루트 CMD에서 실행한다.

```cmd
update_market_data.bat
update_market_data.bat history
update_market_data.bat value
```

위 세 명령은 각각 전체 갱신, 일봉만, 재무만이며 필요에 맞게 하나를 실행한다. 재무만으로 TTM 전환을 완료한 뒤 매매 프로그램을 재시작해 새 후보를 로드한다.

강제 재검증:

```cmd
"%USERPROFILE%\anaconda3\envs\marketdata\python.exe" collect_value_fundamentals.py --limit 0 --force
```

`value_quality.db`, `market_history.db`, `data/value_cache`를 삭제하지 않는다. 완료 상태는 기존 DB에 테이블을 추가해 저장한다. `api_requests`, `cache_hits`, `resumed`, `resumed_saved`, `elapsed_seconds`로 변경 효과를 확인한다. 요청 수는 DART 기준이고 KRX 요청은 별도이며, elapsed_seconds는 종목 처리 루프만, total_elapsed_seconds는 KRX·공시 조회를 포함한 전체 재무 수집 시간을 측정한다.
